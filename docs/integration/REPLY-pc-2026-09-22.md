## 1.【依頼 1】Purchase の `externalId` を UUID にする — 同意

`ocr:purchase:{年月}-{伝票番号}-{行番号}` → **`ocr:purchase:{rowUuid}`**。
[transaction-import.md](transaction-import.md) §4 を書き換えた。

**こちらの当初案（消えた `externalId` を void にせず重複候補として警告）だけでは足りない、という
指摘が正しい。** 危ないのは消える側ではなく衝突する側で、`rows[i] = rows[i - 1]` の挙動と
`rowNumber = index + 1` の再採番まで挙げてもらえたので判断できた。位置ベースのままだと
[transaction-import.md](transaction-import.md) §10 の「未編集なら更新」がそのまま
**別商品での黙った上書き**になる。ワンタップの日常操作でそれが起きるのは受け入れられない。

**トレードオフ（UUID は再作成に弱い）はこちらで受け止める。** 月をまるごと入力し直したときに
全行が新しいキーで届く件は、§2 の 2 つ目の機構（重複の可能性）で拾う。
**そちらに追加の実装は要らない。**

`schemaVersion` は**上げない**。フィールドの追加・削除が無く値の作り方だけが変わること、
連携機能が未実装で**出回っているファイルが 1 つも無い**ことから、移行対象が存在しないため。

> 補足：`externalId` の文字種は `[a-z0-9:_-]`（§4 要件 4）のまま。
> Java の `UUID.toString()` は小文字なのでそのまま通る。**大文字は契約違反で弾かれる**ので、
> どこかで `toUpperCase` していないことだけ確かめてほしい。

## 2.【依頼 2】PC 側ガード — 同意・実装した

> 同じ `externalId` が未編集で存在し、かつ**借方科目（`accountKey`）または `note` が変わっている**
> 場合は、黙って更新せず「要確認」に回す。

入れた。契約は [transaction-import.md](transaction-import.md) §10。**貸方の `accountKey` も同じ扱い**に
してある——Deposit の出金行は相手科目が借方に来るとは限らず、借方だけ見ると片側で抜けるため。

- ユーザーに出るのは**編集済みのときと同じ 3 択**（取込値で上書き／このまま維持／別の取引として追加）。
  採番がずれて別商品が入ってきた場合は「別の取引として追加」を選べば、元の仕訳も残る。
- 既定は「このまま維持」。何も選ばずに閉じても帳簿は壊れない。

**あわせて、もう 1 つ入れた（依頼にはなかった分）**：

**重複の可能性**——`externalId` が未知の行でも、**日付・金額・借方貸方の `accountKey` が既存の
取込行と同じ**なら「要確認」に回す（`DuplicateOfExternalId`）。UUID 方式の弱点（月の入力し直し）に
対する受け皿で、取り消し済み（`IsVoided = 1`）の取引とは突き合わせない——消したものを
入れ直したのなら、それは重複ではないため。

この 2 つで「編集に強い（UUID）／再作成に強い（重複検知）」の両方が揃う。

## 3.【依頼 3】Deposit の合成番号 — 同意。ただし条件が 2 つ

合成番号を入れて `externalId` を 1 本にする方針に同意する。フォールバック規則は契約に置かない。
`UNIQUE(transactionDate, transactionNumber)` ＋ `insertAllIgnoreDuplicates` で**空欄の 2 件目以降が
無言で落ちていた**という指摘は、こちらでは追えない所だったので助かった。取込漏れの修正と
`externalId` の確定を同時に片付けられるなら、そちらの案のほうがよい。

**条件 1：`#` は使えない。** `externalId` の文字種は `[a-z0-9:_-]`（§4 要件 4・§11 の検証項目）で、
`#01` を入れたファイルは**行ごとではなくファイルごと弾かれる**。加えて PC 側は `#` を
「別の取引として追加」の連番サフィックス（`ocr:deposit:2026-02-05-0012#2`）に予約している。
`x01` / `s01` / `-01`（`{日付}-{番号}` の区切りと紛れない形）などにしてほしい。

**条件 2：同じ CSV を取り込み直したら同じ番号になること。** 合成番号を「その日の中の位置」だけで
振ると、**範囲の違う CSV**（前月末からの重なりがある通帳ダウンロード等）を取り込んだときに
同じ取引の番号がずれ、PC には別取引として届く。日付・金額・摘要・**残高**で既存行を先に
突き合わせてから空き番号を振る、という形にできると確実。

> 残るリスクは §2 の重複検知が拾うので、致命傷にはならない。ただし「要確認」の件数が増えるだけ
> 損なので、番号が安定しているに越したことはない。

暫定案（`-noseq`）は採らなくてよい。合成番号でいってほしい。

## 4.【依頼 4】往復検証・手順 3 — 実施した

`examples/transactions.sample.json` を**そのまま**取り込んだ。DB は**本番の複製**
（2026 年分・仕訳 0 件・実データの科目 64／摘要 107）。

```
行数     : 7（新規 7 / 更新 0 / 変更なし 0 / 取消済み 0）
要確認   : 7
契約違反 : 0
```

**契約検証は 7 行とも通った。** 中身の解決結果は次のとおり。

| 見たもの | 結果 |
|---|---|
| `accountKey` の解決 | **キーが入っている借方・貸方はすべて解決できた**（`hiryou` / `kaikake` / `einou` / `suitou` / `douryoku` / `zappi` / `genkin` / `syozairyou` / `mibarai`）。解決できなかったのは**例がわざと `null` にしている 1 行の借方**だけ |
| `memoKey` の解決 | **全滅**。例の `memo-0006` 等が実機に存在しないため |
| `accountName` のエコー | 食い違い無し（`StaleNameDetected` は立たず） |
| `contentHash` | 例のダミー値なので「マスタが一致しません」の警告が出る＝**意図どおりの発火** |

**`memoKey` が解決できないのは契約違反ではなく、例が作り物だから。**
実機の `memoKey` は **`memo-<連番>`（`memo-102`・ゼロ埋め無し）** で、例の 4 桁ゼロ埋めは
説明用に作った値。`memoKey` は不透明キーなので**桁数や形を当てにしないでほしい**
（[vocabulary-snapshot.md](vocabulary-snapshot.md) §4.8 に明記した）。

**実キーに置き換えた版でも試した**（`memo-102` 肥料購入／`memo-63` 農協売上入金／`memo-107` 修理代）：
3 行とも `Matched` で解決し、**確定して仕訳になるところまで通った**。
再取込すると「変更なし」で素通りし、§2 の 2 機構もそれぞれ実際に発火することを確認している。

→ **手順 2（そちらが `vocabulary.json` を取り込む）に進んでよい。**
そちらの UI ができたら、こちらで本物の `vocabulary.json` を書き出して渡す。

## 5. §9-2（「そのとき見た `name`」を接続キーの行に持たせた）について

**異論なし。** 学習エントリの葉ではなく `yayoi_accounts.accountKey` / `rakuraku_tekiyou.memoKey` の
行に持たせるほうが、そちらの資産（商品名 → 科目）を壊さずに済む。
契約が求めているのは「**名前が変わったキーを通る仕訳が 1 件残らず `UnmatchedAccount` で届くこと**」
だけで、それが満たされるならスマホ内部の粒度はそちらの判断でよい。

その表現で言うと、こちらが見ているのは次の 2 つ：

1. `matchStatus` に出てくること（そちらの機構）。
2. 万一 1 をすり抜けても、`accountName` / `memoName` のエコーが現在名と食い違えば
   **その行を「要確認」に回す**（こちらの機構。[CHANGELOG.md](CHANGELOG.md) 2026-09-22 minor）。

§8-0 に書いてもらった「エコーはエクスポート時点のスナップショットから引く」という実装なら、
2 が鳴るのは「古いスナップショットのまま出力した」ときだけになる。意図どおり。
