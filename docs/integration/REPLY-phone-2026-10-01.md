## 1. 背景

### 1.1 スマホの今の作り（minor（9）対応後）

- レシートの品目グループ（同じ商品名をまとめたもの）に、あおいろの科目と摘要を 1 つずつ持たせています
- 帳簿はレシートごとの支払方法の科目で決まります。現金なら `Cash`、未払金なら `Unpaid`、事業主借なら `Transfer` です
- ところが摘要は帳簿ごとに別のレコードです。グループに付けた摘要の帳簿と、レシートの帳簿が違うことがあります
  - 例：既定の支払方法が事業主借なので、グループには振替の摘要「農薬」（借方＝農薬衛生費・貸方＝事業主借）を付けた
  - ところが、そのグループに入るレシートの 1 枚が現金払いだった
- このとき、スマホは送る帳簿の中から次の条件をすべて満たす摘要を探して置き換えています
  - 同じ経費科目
  - 同じ**名前**・同じ税率・同じ事業割合
  - 見つからなければ `memoKey = null`（`UnmatchedMemo`）で送ります

### 1.2 何がまずいか

- **名前で探している**。vocabulary-snapshot §4.8 の「摘要の名前は改名され得る・重複し得るので参照キーにしない」に反します
- **実機では名前がそろっていない**。振替は「農薬」、現金/出金は「農薬購入」なので、置き換えが当たらず摘要なしになりました
- **同じ名前でも事業割合が違うことがある**。摘要は事業割合を運ぶ（§4.7）ので、名前は手がかりになりません。
  今のスマホは事業割合まで一致を見ているので取り違えはしません。ただ、そのぶん外れやすくなります
- **農家から見て複雑**。農家が摘要を選ぶのは 1 回なのに、支払方法しだいで送られる摘要が変わったり消えたりします。
  名前をそろえて 3 帳簿に同じ摘要を作れば当たりますが、事業割合を 3 か所で保つ手間と、ずれる危険が残ります

### 1.3 レシートの支払方法は 3 つ

minor（9）の合意で、レシートの貸方は現金（`Cash`）・未払金（`Unpaid`）・事業主借など（`Transfer`）の 3 つになりました。
預金・買掛金は扱わない約束です。
レシートの借方はどの帳簿でも「経費」で、帳簿によって違うのは貸方だけです。
**摘要が決めたいもの（経費の科目・事業割合・インボイス既定・名前）は、どれも借方の側にしかありません。**
なので、1 件の摘要を 3 帳簿で共有しても意味が崩れないと考えています。

## 2. 依頼：経費の摘要を 3 帳簿で共有する

### 2.1 スマホが必要なこと

- レシートの明細 1 行に、**帳簿（支払方法）が何であっても同じ `memoKey`** を入れられること
- PC がその `memoKey` を解決したら、次のように仕訳を組むこと
  - 借方の科目 ← 摘要の相手科目（経費）。スマホが送る `debit.accountKey` と同じものです
  - 事業割合・インボイス既定 ← 摘要の値（今の §4.7 と同じ）
  - 貸方 ← 取込行の `credit.accountKey`（現金・未払金・事業主借）
  - 帳簿 ← 取込行の `ledgerType`（minor（9）のまま）
- vocabulary で、どの摘要がどの帳簿で使えるかがわかること

### 2.2 提案する形（PC 側で決めてもらってかまいません）

現金と預金を共有する今の仕組みを、未払と振替まで広げる案です。

- `MemoTemplate` に印を 2 つ足す：`ShowInUnpaid`・`ShowInTransfer`。vocabulary にも `showInUnpaid` / `showInTransfer` として出す
- 印を付けられるのは「経費の出金の摘要」だけにする
  - `ledgerType` が `Cash` または `Bank`
  - `direction == "Out"`
  - `counterAccountKey` が経費の科目
- 意味
  - `showInUnpaid = true` → 未払/発生（`Unpaid` × `In`）としても使える。借方＝相手科目、貸方＝未払金
  - `showInTransfer = true` → 振替としても使える。借方＝相手科目、貸方＝**取込行（手入力なら入力欄）の貸方の科目**
- 振替の摘要は貸方を自分で持つ作りです。一方、共有の摘要は貸方を持ちません。
  共有の摘要の `debitAccountKey` / `creditAccountKey` は今の非振替の摘要と同じく `null` のままにして、
  `ledgerType` も `Cash` / `Bank` のままにする想定です
- フィールドを足すだけなので、`schemaVersion` は 2 のまま minor で足りると考えています（印の無い古い vocabulary は両方 `false` 扱い）

別の形として、帳簿に結びつかない「経費の摘要」という種類（`ledgerType` の新しい値）を作る案も考えました。
ただ、`ledgerType` の値が増えると、スマホも PC も分岐が増えます。今の `showIn*` を広げるほうが小さく済むと考えています。

### 2.3 今の振替の摘要（「家計より支払」6 件など）

そのまま残してかまいません。スマホは、帳簿が `Transfer` のときの候補に、今の振替の摘要も含めます。
条件は今と同じで、`debitAccountKey == 経費` かつ `creditAccountKey == 貸方` です。
ただ、農家に勧めるのは共有の摘要にします。

## 3. 質問

- **Q1**：§2.2 の形（`showInUnpaid` / `showInTransfer`）で受けられるか。別の形がよければ教えてほしい
- **Q2**：取込のときの扱い。`memoKey` の摘要の `ledgerType`（例：`Cash`）と行の `ledgerType`（例：`Transfer`）が違う。
  それでも、印が付いていれば `Matched` として確定できるか。印が無い組み合わせ（例：`showInTransfer = false` の摘要を `Transfer` で送った）は、
  `UnmatchedMemo` 相当の要確認になる、という理解でよいか
- **Q3**：振替で共有の摘要を使うとき、事業割合は摘要の `businessRatio`（借方側）を仕訳に入れる、でよいか。
  貸方（事業主借）側の事業割合・税率は、今の振替のレシートと同じ扱い（税率 `null`）でよいか
- **Q4**：PC の手入力の画面（未払帳・振替伝票）の摘要ドロップダウンにも、共有の摘要を出すか。
  スマホとしてはどちらでもかまいません。農家が PC で同じ経費を手入力するときにも便利だと思うので、ご判断ください
- **Q5**：既存の摘要の印は、最初はすべて `false` で始まり、農家が摘要登録画面で付ける、でよいか。
  「現金/出金かつ相手科目が経費」の摘要に最初から印を付けておく（プリセットや移行で）という考え方もあります

## 4. スマホ側の予定（§2 の合意後）

- レシートの品目グループ・明細の個別変更で選べる摘要を、次の 2 つにする
  - 3 帳簿で共有できる摘要（`showInCash` かつ `showInUnpaid` かつ `showInTransfer`、`direction == "Out"`）
  - 帳簿に合う従来の摘要
- 共有の摘要の `memoKey` は、支払方法が何でもそのまま送る。§1.1 の**名前による置き換えはやめる**
- 共有でない摘要が、そのレシートの帳簿で使えないときは、`memoKey = null`（`UnmatchedMemo`）で送る。
  名前では探さない。画面にも「この支払方法では摘要なし」と出す
- vocabulary に印が無い（古い PC の）ときは、今の動きのまま

## 5. 報告：minor（9）への切り替え（スマホ側・実装済み）

- `ledgerType` を貸方の科目の `ledgerAffinity` で決めるようにした（`Cash` / `Unpaid` / それ以外は `Transfer`）。
  返品は入れ替える前の貸方で決める
- `Transfer` のときは振替の摘要（`debitAccountKey == 経費`・`creditAccountKey == 貸方`）を候補にした
- 支払方法のルールに当たらないときの既定の科目を選べるようにした（今までは現金固定）。
  選んだ科目が辞書から消えたら、現金にはせず貸方未設定で送り、画面で警告する
- 支払方法の科目の候補から、預金・買掛金を外した（PC 回答 §1）
- **まだ直していないこと**：`debit.taxRate` に、今も摘要の `taxRate` を入れている（購買・通帳・レシートの 3 部門とも）。
  §4.7 の決め方（レシートの税率マーク → 科目の `defaultTaxCategory`）とは違います。
  PC 回答 §5 で「摘要の `taxRate` は見なくてよい」とあったので、§4 の作業のときにあわせて §4.7 の決め方に直します
- 実機での確認は途中です。PC の振替伝票に入ることの確認も、これからです
