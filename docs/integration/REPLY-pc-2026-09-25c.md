## 2. Deposit の `externalId`

提案どおり `ocr:deposit:p{passbookId}-{transactionDate}-{transactionNumber}` にした（契約 §4 の表）。

- PC は `externalId` を不透明な文字列として扱い、`ocr:deposit:` の中身を読んでいない。**PC のコード変更は無い**
- サンプル `examples/transactions.sample.json` の 3 件を `ocr:deposit:p1-…` に書き換えた
- 過去の回答（`REPLY-pc-2026-09-22.md` の `#2` の例など）は当時の記録なので書き換えていない

**口座を付け替えたときの PC の動き**（通帳 ID を `bankSlotNo` と分けた狙いどおりになるかの確認）：

- 同じ `externalId` なので**同じ取引として受ける**（新しい行は増えない）
- まだ「要確認」にある（確定前）なら、黙って新しい口座に更新する
- **確定済みなら黙っては更新しない**。預金側の `accountKey` が変わるので、§10 の「別の取引になった」
  判定に当たり、「取込値で上書き／このまま維持／別の取引として追加」の 3 択をユーザーに出す。
  帳簿の口座が動く変更なので、確認を挟むのが正しいと考えている

## 3. Q1：口座間の振替

**読みは合っている。スマホ側は何もしなくてよい。**

- 営農口座 → 直売口座の振替は、どちらの通帳から組み立てても 借方＝直売口座・貸方＝営農口座 になる。
  日付・金額・借方貸方の `accountKey` がそろうので「重複の可能性」に当たる
- 条件は**相手科目にもう一方の口座を選んでいること**。片方だけ別の科目（事業主貸など）にしていると
  そろわないので鳴らない

**PC 側の穴（直した）**：これまで「重複の可能性」は、**すでに DB に入っている取込行**とだけ比べていた。
2 冊を別々のファイルで取り込めば 2 本目で鳴るが、**2 冊ぶんを 1 つの `transactions.json` に入れると
両方とも素通りして二重計上**になっていた。いまは同じファイルの前の行とも比べる。

- 後の行が「重複の可能性」になり、相手の `externalId` が付く。先の行は普通に入る
- 取込サマリーの警告にも「口座間の振替を両方の通帳から取り込んだときも同じになります」と出す
- 本番の複製（使い捨て）で確認した：p1・p2 の振替 2 行を 1 ファイルで取り込むと、
  `ocr:deposit:p2-2026-04-01-0020` が「重複の可能性（`ocr:deposit:p1-2026-04-01-0020`）」になる。
  同じ日・同じ通番でも通帳が違えば別の行として 2 件入る（§2 の依頼どおり）

スマホ側で振替を除外しない方針のほうがよいと考えている。片方の通帳しか取り込まない月もあるので、
スマホが勝手に落とすと、その月は振替が帳簿から消える。
