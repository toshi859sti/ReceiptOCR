## 1. 何を予測し、何を予測しないか

商品名・通帳摘要から確実に予測できるのは**科目だけ**。他の項目は「予測」ではなく別ソースから決まる。

| 項目 | 本当の出所 | スマホの担当 |
|---|---|---|
| **科目**（`accountKey`） | 商品名・通帳摘要（ルール＋学習、必要なら LLM 補助） | 解決する |
| **インボイス**（`hasInvoice`） | **レシート現物**（適格請求書登録番号 `T\d{13}` の有無） | OCR で判定（予測でなく事実）。プリセットの `hasInvoiceDefault` は最後の手段 |
| **税率**（`taxRate`） | レシートの税率マーク ＞ 摘要の `taxRate` ＞ その `accountKey` の `defaultTaxCategory` | 上から順に決める（§4 の 5・[vocabulary-snapshot.md](vocabulary-snapshot.md) §4.7）。不明なら `null`＋`matchStatus` |
| **事業割合**（`businessRatio`） | **その農家の家事按分方針**＝摘要辞書の `businessRatio`（商品と無関係） | **触らない。`100` 固定で出す**。PC は `memoKey` が解決できたら**摘要の値を採る**（[vocabulary-snapshot.md](vocabulary-snapshot.md) §4.7） |
| **摘要**（`memoKey`） | 摘要辞書（科目からの逆引き） | **閉じた語彙**：辞書の `memoKey` か `null` の二択。生テキストは `note` へ。任意でラベル選好キャッシュ（§5） |

**帰結**：摘要辞書（`memoTemplates`）の逆引きは「記帳バンドルを取る」ためではなく
**摘要ラベルの候補出し専用**に格下げされる。科目は `accountKey` から直接引ける。税率は摘要が決まればその値を使う
（[vocabulary-snapshot.md](vocabulary-snapshot.md) §4.7）。

## 2. ルールエンジンで完結する範囲

| source | ルールだけで足りるか | 理由 |
|---|---|---|
| **通帳（預金出納帳）** | ほぼ完結（数ヶ月で 95%+） | 定期引き落とし＝同じ摘要文字列・近い金額・毎月。電気/水道/電話/燃料/JA 引き落とし/共済/借入返済/税金 |
| **JA購買伝票** | ほぼ完結 | **選択肢が少なく語彙が閉じている**（買掛/仕入の摘要は 10 件・指す科目は 8 つ。JA の購買品目は毎年ほぼ同じ）ので、初月に数十件確定すれば以後は学習で回る。⚠ 伝票に「肥料/農薬/…」の摘要カラムは**無い**——取れるのは商品名・金額・領収日と、小計行の分類 `一般購買`/`給油所`/`農業機械` の 3 つだけ（§5「組み込み」） |
| **店舗レシート** | 頻出品はカバー、裾野は初回入力 | 任意の商品名は長い裾野。初見は「ユーザーが1回分類」→ルール化 |

**弥生・freee・マネーフォワードも LLM 以前からこの領域を「自動仕訳ルール／学習」でやってきた。**
LLM なしで成立する。

## 3. ルールの型

| 型 | キー | 例 |
|---|---|---|
| 正規化文字列一致 | `正規化摘要` | `"デントウ" → …`（※これ単独では金額違いで衝突しうる） |
| **文字列＋金額バンド** | `(正規化摘要, 金額 min..max)` | `("デントウ", 4000..6000) → douryoku` / `("デントウ", 1500..2500) → zigyounusikas` |
| 文字列＋口座＋方向 | `(摘要, bankSlotNo, In/Out)` | 営農口座の JA 入金 → `suitou`、家計口座は別扱い |
| 部分一致／正規表現 | `contains` / `regex` | `contains("ノウキョウ") && In → urikake` |
| 分割 | `(摘要, 金額) → 借方A n% / 事業主貸 (100−n)%` | 電話 1 本を通信費 60%／家事 40% |

- 正規化＝全角半角統一・カナ統一・空白除去・日付/連番ノイズ除去（決定論的関数）。
- 金額バンド＝前回確定額 ± 許容幅（例 ±20% か ±1000 円）。
- **「大きい方＝事業用」は AI 推論でなく金額バンドルールで表現する**（母屋のほうが電気を食う農家もいる＝
  一般原則にできない。農家固有の事実は確定1回でルール化する）。

## 4. 照合パイプライン（LLM なし）

1. OCR 行を正規化。
2. 特異度順にルール検索：
   `摘要+金額+口座+方向` → `摘要+金額` → `摘要+口座` → `摘要` → `contains/regex` → フォールバック。
3. 最初にヒットしたルール（confidence 閾値以上）を適用：`accountKey`。
4. **摘要** ＝ 決めた `accountKey` から `memoTemplates` を逆引き（[vocabulary-snapshot.md](vocabulary-snapshot.md) §4.2）。
   1 件→その `memoKey`／複数→近い候補の `memoKey`＋`Ambiguous`／**0 件→`memoKey = null`＋`UnmatchedMemo`**。
   `memoKey` は辞書のキーか `null` の二択（スマホは文字列を作らない）。生テキストは `note` へ。
   ルールに `memoKey` を持たせておけば逆引きを飛ばして直接確定できる（定期取引向け）。
5. **税率** ＝ レシートの税率マーク（未実装でよい）→ 4 で決まった摘要の `taxRate` →
   その `accountKey` の `defaultTaxCategory` を [README.md](README.md) §4 の変換表で（経費科目だけ）→ `null`。
   収入科目は摘要が無ければ `null`（[vocabulary-snapshot.md](vocabulary-snapshot.md) §4.7・2026-10-02 minor（11））。
6. **事業割合** ＝ `100`（PC は解決できた `memoKey` の摘要の値で置き換える。§1）。
   ⚠ 事業割合だけ違う摘要（電気料金 40／電気料金（事業専用）100 など）が候補に並んだら、
   4 の「近い候補」で自動確定せず `Ambiguous` にするかユーザーに確定させる。
7. **インボイス** ＝ レシート OCR の `T\d{13}` 検出結果。無ければ `hasInvoiceDefault` か `matchStatus`。
8. 科目がヒットなし → `matchStatus = "UnmatchedAccount"`、推定値があれば入れて PC の「要確認」へ。

## 5. ルールはどう作られるか — 「確定例 → ルール再コンパイル」

**基本は自動生成。ユーザーが手で書くのは例外（逃げ道）。**

ルールを直接ミューテートせず、**確定例を貯めてそこからルールを再生成する**方式：

```
確定例テーブル（生の確定・不変ログ）        ルール（導出物・再生成可能）
─────────────────────────────────         ─────────────────────────────
正規化摘要 / 金額 / 口座 / 方向 / source     特異度つき述語 → accountKey
確定した科目・税率・摘要 / 確定日時 / 由来       confidence / ヒット数 / 最終使用 / 由来した確定例ID / is_manual
```

- レビュー画面でユーザーが確定・訂正するたびに**確定例を1件追加**。
- バッチ確定後に「同じ正規化摘要でグルーピング → 一貫性チェック → ルール発行」を走らせる。
- 再コンパイル方式にする理由：再導出可能・デバッグ可能・衝突を**再分析で**解消できる（in-place 更新だと
  フリップフロップする）。

### 衝突 → 自動精製（デントウ 5000/2000 の例）

| 回 | 確定 | エンジン |
|---|---|---|
| 1 | `デントウ 5000 → 動力光熱費` | `("デントウ") → douryoku`（摘要のみ・暫定） |
| 2 | `デントウ 2000 → 事業主貸` | **矛盾検知** → 2例の差分を解析 → 金額が大きく違う → 両方を金額バンドルールに自動精製 |
| 3〜 | — | 金額で自動振り分け。LLM もユーザー操作も不要 |

差分に明確な特徴が無ければ精製せず「曖昧」フラグ → 次回両候補を出して1タップで選ばせる
（その選択がさらに細かい特徴を足す）。**黙って上書きしない。**

### 確信度の段階

- 確定1回 → 暫定ルール（自動適用するがレビュー画面で「推定」表示・訂正しやすく）。
- 一貫した確定2〜3回 → 確信・以後は黙って自動適用。
- 誤タップ1回で全体が汚染されるのを防ぐ。

### 確定はどこでやるか

**スマホのレビュー画面**（マッチングエンジンとルールがそこにある）。契約でも「個別上書きを適用済みに
してから出力」（[README.md](README.md) §1 責務 5）＝スマホ側にレビュー工程がある前提。
PC の「要確認」は取りこぼしの安全網であって主戦場ではない。

- PC 側で直したい運用にするなら、将来 `corrections.json`（PC → スマホ・`externalId → 訂正後 accountKey`）を
  追加してループを閉じる。現時点では必須でない。

### 組み込み（学習不要）

JA購買伝票の**小計行の分類**だけが固定表で効く（2026-09-23 訂正：以前は「伝票の摘要カラム
（肥料／農薬／諸材料／種苗／飼料）」と書いていたが、実物の伝票〔島原雲仙農協 購買代金請求明細書〕に
その列は無い）。

| 分類 | 科目 |
|---|---|
| `給油所` | ほぼ動力光熱費（ガソリン類） |
| `農業機械` | 農具費 か 修繕費 の 2 択 |
| `一般購買` | 決まらない。**商品名から**肥料費・農薬衛生費・諸材料費・種苗費・飼料費などへ（学習） |

共済・電気・水道などの通帳パターンは農家ごとに違うのでシードしない（学習に任せる）。

### 手書きルール（任意・opt-in）

パワーユーザー向けにルールエディタを用意してよい：初回取込前の先出しシード／学習ミスの修正／
exact より一般化する `contains`/`regex` ルール。**大半のユーザーは触らない。**

## 6. マスタ変更（無効化・作り替え・改名）との整合

- ルールは `accountKey`（摘要を指すなら `memoKey`）で参照先を持つ。`vocabulary.json` 取込時、
  **参照先のキーが新しいファイルに存在しなくなったルール・確定例はスタール（無効）フラグ**を立てる。
  科目の無効化でも作り替えでもキーが消えるので、この 1 ルールで両方に対応できる
  （[vocabulary-snapshot.md](vocabulary-snapshot.md) §4.6・§4.8）。
- `name` だけ変わったキーは、その `accountKey` に紐づくルールを「要再確認」に落とす（保険）。

## 7. LLM の位置づけ

- **スパイン＝ルールエンジン**（決定論的・オフライン・課金なし）。
- **LLM は任意プラグイン**：未ヒット行の初回サジェスト、店舗レシートの品名 → カテゴリ推定。
  使わなくても回るが、初回入力の手数が増える。
- LLM を使う場合も**バッチ処理**（1明細まとめて＋候補に絞った語彙を1リクエスト）。1行ごとに全語彙を
  添付して呼ぶ・画像を何度も送る、は避ける。定期引き落としは2〜3ヶ月で全部ルール化されるので
  以降 LLM を呼ばない。
